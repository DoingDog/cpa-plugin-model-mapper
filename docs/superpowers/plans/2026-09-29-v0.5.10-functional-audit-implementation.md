# v0.5.10 功能审计修复实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 消除大块分片 raw JSON/Gemini 数组流的重复复制与扫描，并让本地 smoke 在 CPA 关闭失败时返回失败。

**Architecture:** `streamChunkRewriter` 在首次识别未完成复合 JSON 值时复制输入到自有缓冲，后续分片追加到同一缓冲并只扫描新增字节，完成后沿用既有 `tryRawJSONChunks`/`writeRawJSONArray` 校验与输出。`stopCPA` 检查主动中断后的真实退出状态，只豁免预期 SIGINT；保留跨平台强制终止逻辑。

**Tech Stack:** Go 1.26、标准库、已有 Go 单元测试、`c-shared` 插件 ABI、CLIProxyAPI/v7 v7.2.152。

**Spec:** `docs/superpowers/specs/2026-09-29-v0.5.10-functional-audit-design.md`

## Global Constraints

- [ ] **Step 1: 添加失败回归测试。** 在 `main_test.go` 新增 `TestStreamChunkRewriterLargeFragmentedRawJSONAllocations`，用表格覆盖 raw object (`frameRawJSONAsSSE=true`, format=`openai-response`) 和 Gemini raw array (`frameRawJSONAsSSE=false`, format=`gemini`)：各构造约 1 MiB JSON，包含 `{`、`}` 和 `\\\"` 的内容，8 KiB 分片；先验证单次与分片输出字节相同且恢复了 `model`/`modelVersion`；再使用 `testing.AllocsPerRun(1, func() { 每次新建 rewriter，写入同一分片并 Finish })`，对每组断言分配次数 <100。fixture 在计量前生成，输出计数防止优化器消除。另加 `TestStreamChunkRewriterCompletedRawJSONMayCrossPendingLimit`：先写入不超过 16 MiB 的不完整对象，最后一段闭合使完整值超出 16 MiB，期待按原行为输出；已完成前缀与不完整尾部的输出、可变输入所有权及超限错误直接运行现有测试。若原实现分配次数与期望不符，先测基线数值再据明确差距收紧阈值，不以耗时作为单元测试断言。测试核心可直接使用现有 `Write`/`Finish` 接口：

```go
input := []byte(`{"model":"upstream","payload":"` + strings.Repeat(`x{}\"`, 1<<18) + `"}`)
parts := make([][]byte, 0, (len(input)+8191)/8192)
for i := 0; i < len(input); i += 8192 {
    parts = append(parts, input[i:min(i+8192, len(input))])
}
run := func(parts [][]byte) []byte {
    r := newStreamChunkRewriter("client")
    r.format, r.frameRawJSONAsSSE = "openai-response", true
    var output []byte
    for _, part := range parts {
        chunks, err := r.Write(part)
        if err != nil { t.Fatal(err) }
        for _, chunk := range chunks { output = append(output, chunk...) }
    }
    chunks, err := r.Finish()
    if err != nil { t.Fatal(err) }
    for _, chunk := range chunks { output = append(output, chunk...) }
    return output
}
want := run([][]byte{input})
if got := run(parts); !bytes.Equal(got, want) || !bytes.Contains(got, []byte(`"model":"client"`)) {
    t.Fatalf("fragmented output differs from restored complete JSON")
}
var measured []byte
allocs := testing.AllocsPerRun(1, func() { measured = run(parts) })
if allocs >= 100 || len(measured) == 0 { t.Fatalf("allocations=%v, output=%d", allocs, len(measured)) }
```

- [ ] **Step 2: 验证红灯。** 执行 `go test . -run 'TestStreamChunkRewriter(LargeFragmentedRawJSONAllocations|CompletedRawJSONMayCrossPendingLimit)$' -count=1 -v`。预期大分片分配测试因现有重复复制而 FAIL；跨限用例应保持 PASS。
- [ ] **Step 3: 最小实现。** 在 `streamChunkRewriter` 旁新增内部状态，记录扫描偏移、JSON 嵌套深度、字符串及转义状态；首次 `retainPending` 未完成 `{`/`[`/`"` 值后初始化状态。下一次 `Write` 只 `append(r.pending, p...)` 到自有 buffer，扫描新增区间；若仍未闭合，仅此时检查 16 MiB 上限并返回，不重新调用完整 JSON 解析；闭合时清状态并继续既有 `tryRawJSONChunks`/`writeRawJSONArray` 分支。数组中仅未完成元素进入该状态。非 raw 输入维持原路径；`Flush`、溢出及异常时清状态。不得因一次输入出现大量 `}` 字符就重复从头扫描，不要引入新依赖或异步 goroutine。`Write` 的待完成分支遵循以下实际控制流，扫描器的字符串/转义/嵌套状态跨调用保存；新增的内部类型 `rawJSONScan` 至少包含 `active bool`、`scanFrom int`、`depth int`、`inString bool`、`escaped bool`。其 `advance(p []byte) bool` 只检查 `p[scanFrom:]`：非字符串时 `{`/`[` 增加 depth，`}`/`]` 减少 depth；字符串内 `\\` 跳过下一字节，未转义 `"` 结束字符串；根值闭合时返回 true，否则将 scanFrom 更新到 len(p) 并返回 false。只有未完成 JSON 根值以 `{`/`[`/`"` 起始才激活该状态，避免改变普通数值与 SSE 分支。

```go
if r.rawScan.active {
    r.pending = append(r.pending, p...)
    if !r.rawScan.advance(r.pending) {
        if len(r.pending) > maxPendingStreamBytes {
            r.pending = nil
            r.rawScan = rawJSONScan{}
            return nil, fmt.Errorf("stream pending data exceeds %d bytes", maxPendingStreamBytes)
        }
        return nil, nil
    }
    p, r.pending = r.pending, nil
    r.rawScan = rawJSONScan{}
} else if len(r.pending) > 0 {
    p = append(r.pending, p...)
    r.pending = nil
}
```

首次确定未完成的复合值时由 `retainPending` 获得独占副本，扫描器从该副本当前位置起初始化；别把输入切片直接存入 `r.pending`。如果分片已经闭合，本轮先沿既有解析路径处理再决定是否检查未完成上限。

### Task 2: 本地 smoke 正确报告 CPA 异常退出

**Files:**

**Interfaces:**

- Produces: 成功中断后非零普通退出和 Kill 前进程已退出的故障均返回含进程日志的错误；预期 SIGINT、正常退出、Windows 上正常强制 Kill 仍返回 nil。

- [ ] **Step 1: 添加失败回归测试。** 新增 `TestStopCPAReturnsFailureAfterSuccessfulInterrupt`：依照 `TestStopCPAReturnsUnexpectedExitAfterKillRace` 启动独立测试子进程、写日志、设置 `signal` hook 返回 nil 并向 `waitDone` 送入 `errors.New("exit status 2")`，要求 `stopCPA` 错误包含退出状态和日志。新增 `TestStopCPAReturnsFailureWhenKillFindsExitedProcess`：`signal` hook 返回 nil、`waitDone` 在 `kill` hook 执行时收到相同错误、`kill` 返回 `os.ErrProcessDone`；验证不把已经退出的故障当作主动 Kill。两个测试均在 `t.Cleanup` 回收独立子进程；第二个测试走现有 2 秒停止超时，不加新生产代码测试开关。
- [ ] **Step 2: 验证红灯。** `go test .github/scripts/smoke-local.go .github/scripts/smoke-local_test.go -run 'TestStopCPAReturnsFailure(AfterSuccessfulInterrupt|WhenKillFindsExitedProcess)$' -count=1 -v`，预期两个用例都 FAIL，因为现实现返回 nil。
- [ ] **Step 3: 最小实现。** 成功中断后的 select 改为接收 `waitErr`，非 nil 且不是 `*exec.ExitError` 对应 `syscall.WaitStatus.Signaled() && Signal()==syscall.SIGINT` 时调用 `earlyExitError`；否则返回 nil。在 Kill 的 `os.ErrProcessDone` 路径，无论 `interruptErr` 是否 nil，若 waitErr 为非预期中断的异常退出则报告。实际已执行 Kill 的进程仍保持原有处理，不把其预期被杀的退出码误判成崩溃。`syscall.WaitStatus` 在 Windows 与 Unix 的 Go 1.26 中均提供 `Signaled`/`Signal` 方法。判断函数可写成如下最小形式，并只在主动发送中断成功或发现进程已经退出的分支使用：

```go
func expectedInterruptExit(waitErr error) bool {
    var exitErr *exec.ExitError
    if !errors.As(waitErr, &exitErr) { return false }
    status, ok := exitErr.Sys().(syscall.WaitStatus)
    return ok && status.Signaled() && status.Signal() == syscall.SIGINT
}
```

在 `case waitErr := <-proc.waitDone:` 中仅当 `waitErr != nil && !expectedInterruptExit(waitErr)` 时 `return earlyExitError(proc.logFile.Name(), waitErr)`；`killErr == os.ErrProcessDone` 时应用相同规则。`killErr == nil` 且已经主动 Kill 的路径保持原样。
- [ ] **Step 4: 验证绿灯和跨平台逻辑。** 运行上述聚焦命令，再运行 `go test .github/scripts/smoke-local.go .github/scripts/smoke-local_test.go -count=1`；确认现有 `TestStopCPATerminatesRunningProcess` 在当前 Windows 环境不回归，Linux CI 上 SIGINT 路径由同一测试覆盖。若需要 Linux 侧直接验证，使用现有 CI job 而非在本机跳过信号分支后声称已覆盖。
